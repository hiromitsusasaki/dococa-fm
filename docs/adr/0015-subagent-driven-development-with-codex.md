# 0015 サブエージェント駆動の開発と、Codex の第二の目

- **Status:** Accepted
- **Date:** 2026-11-03

## Context

1 人の人間が 5 日で、本番に出せる品質のものを作る必要がありました。Claude Code に全部を 1 つの文脈で書かせると、文脈が膨らみ、同じ思い込みがレビューまで通ってしまいます。

## Decision

計画を Task に分け、`superpowers:subagent-driven-development` で進めます（本人の決定）。

| 役 | 担い手 | 仕事 |
|---|---|---|
| 指示役 | メインのセッション（Opus または Fable） | 設計書と計画を書く。タスクごとに実装者とレビュアーを起こし、指摘を裁く |
| 実装者 | Sonnet（設計判断を含むタスクは Opus） | 1 タスクずつ、テストを先に書いて実装し、ブラウザで画面を確かめる |
| レビュアー | Opus | 仕様との一致・セキュリティ・品質を読み取りだけで見る |
| 第二の目 | Codex（OpenAI、読み取りだけ） | 各 Phase の最後に全体の diff を読む |
| 本人 | 人 | 設計書の承認、本番を聴いての差し戻し、push とデプロイ、公開 |

- タスクごとに新しい実装者とレビュアーを起こす。Sonnet が同じタスクで 2 回失敗したら Opus でやり直す。
- 裁定は台帳に、理由と「間違っていたときの費用」と一緒に残す。
- 計画と実装がずれたら、計画を先に直す（計画が正本）。

## Consequences

- 別のモデル・別の文脈で読ませることが、安い保険になった。Claude 側と Codex 側の指摘は重なりが少なかった。たとえば Phase 5 では、Codex が「既存の利用者に公開 URL が付かない」を、Claude 側が「失敗し続ける行への無限課金」を見つけた。
- レビューの指摘を断ることもある。断った理由も台帳に残る。
- 並行に走らせると、共有ファイルの差分が別のタスクの commit に混ざる事故があった。以後、指示役は明示したパスだけを commit する。
- 台帳の全文とレビューの経過は公開リポに置いていない。設計書の追記 A〜O が、本人の差し戻しで何が変わったかの公開の記録になっている。

## 0. 一文

**自分が好きなものを好きな人が世界のどこかにいて、その理由が知れたら、人生がちょっとだけ豊かになる。**（本人、2026-11-03）

Dococa FM は、世界のどこかの誰かが置いた「その曲・本・映画と自分」の一言を、あなた一人のために組まれたラジオ番組にして流す。
タグライン: 「世界のどこかにいる誰かの好きなものが聴こえてくるラジオ」（本人決定 2026-11-05。旧案「世界のどこかの、好きなものが流れてくるラジオ」を置き換え） / "Somewhere, someone loves this too."

## 1. 意図（なぜ）

- 音楽・本・映画の話を同じ熱量でできる相手がいない。これは好みが合う人が居ないのではなく、(1) 同じ時間に同じ場に居ない、(2) 熱量差が見えると話せない、(3) 話したいのは一致ではなく「それと自分の物語」だから（notes/28 §2）。
- 海外は「好みの一致で人を結ぶ」製品が混雑し（Music Mate、MusicBuddy、EQUALS、Mosh）、失敗の型が出ている: 一致率は浅い、チャットルームは死ぬ、AI の生成 MC は嫌われる。「曲と物語を時間差で一人に届ける」「お便り（ラジオ）」の形は空いている（notes/28 §3）。
- 本人のこの関心は 7 年続いている（2019 DJ ブース → 2020 musico → 2025 バーチャル DJ → 2026 Mix と digline）。本人が最初の利用者になれる（notes/28 §1）。
- 深夜ラジオの作法（お便り、ラジオネーム、DJ が読む、返事は義務でない、聴くだけでいい）は、ゆるいコミュニティを AI が仕切る形として既に文化がある。
- **なぜ今か（本人、2026-11-03）**: AI が工場のようにコンテンツを一瞬で大量に作る時代に、人が自分の「好き」を自分の言葉で置くことには、逆に存在する意味がある。本人が一貫して追ってきた「AI が何でもやる時代に人間に残されたもの」（物語、主観、好き嫌い）の文脈に、この製品は正面から乗る。DJ は AI だが、番組の中身は全部、人が置いた一言である。

## 2. ゴール / 非ゴール / アンチゴール

**ゴール（v1、11/8 まで）**
1. 聴く人が、アプリを開くと自分のための番組が流れ、画面に紹介中の曲・本・映画が出る。仕事中の BGM にできる。
2. 聴き終えたあと、嬉しくなる・癒される・その作品をもう一度体験しに行ける（外部サービスへの送り出し）。
3. 誰でも一行の「お便り」を置ける。白紙に書かなくて済むよう、自分の履歴（Spotify）が先に入るか、作品の URL を貼るだけで作品が立ち上がる。
4. 作品のページに世界の一言が溜まり、DJ の紹介が声の数だけ豊かになる。
5. リアクション（「私も」と一言）が、数ではなく「どこかの誰か」として本人に見え、DJ の紹介に戻ってくる。
6. 同じ台本が三つの出口から出る: アプリの画面、クラウド TTS、MCP（Claude / ChatGPT / Gemini / 個人のアシスタント）。
7. 審査員が自分で試せる: 好きなものを 3 つ入れるか作品 URL を貼ると、1 分で自分の回ができる。

**非ゴール（v1 では作らない）**
- 時間固定の生放送。v1 は「あなたのための回」をその場で生成し、アーカイブに残す。
- 英語 UI と英語 DJ。構造だけ用意し、日本語で出す。
- Apple Music 連携、Bandcamp / Letterboxd / Goodreads の API 連携。CSV の取り込み（Netflix / Goodreads 等）は v1 から外す（本人決定 2026-11-03、URL 貼り付けで代替）。
- ブラウザ拡張。v1 は URL 貼り付けとブックマークレットまで。拡張は次の版。
- ネイティブアプリ（v2 候補。§2.1）。v1 は Web。PWA にして Media Session API でロック画面の再生操作とバックグラウンド再生を取る。
- 曲のフル再生・ミックス。30 秒の公式プレビューと埋め込みのみ。

**アンチゴール（できても失敗）**
- 人と人の DM、プロフィール、一致率、マッチング。ラジオネームと土地だけの関係を超えない。
- いいね数、ランキング、人気順。数字で人や作品を測らない。
- お便りの要約・言い換え・自動配信。原文のまま読む。
- 出典の無い「見つけた声」。架空のお便り。
- 時事（日付、ニュース、流行、季節の挨拶を含む）。番組は時間の外にいる。
- 全てを好みに最適化すること。「遠く」の枠は常に残る。

### 2.1 v2 候補（本人の提案 2026-11-03。要深掘り。v1 には入れない）
- **自分の「好き」を集めた番組を固定 URL で公開し、プロフィール等に貼れる**（本人の許可制）。出会いやコミュニケーションはこのサービスではやらないが、「私の好きなもの」の提示は、番組という器なら押しつけにならない。
- **トップページを公開番組の一覧やタイムラインにする**案もある。v1 のトップは「番組を聴く」「一通置く」だけにし、データ構造だけ公開に備える（episode に公開フラグを後から足せる形。リスナーのラジオネームを URL に使える形）。
- **ネイティブ化（本人提起 2026-11-03、Claude の提案を本人了承）**: この Web を Capacitor で包み、DJ の声を OS 標準の高品質音声（iOS/macOS の AVSpeechSynthesizer 拡張音声、Android の Google TTS）や端末内モデル（Kokoro-82M の Core ML 版。日本語あり、INT8 で約 80MB、iOS 18 以上）に差し替えられるようにする。iOS の Personal Voice（自分の声）もここで選べる。バックグラウンド再生・ロック画面・CarPlay は「仕事中の BGM」に効く。v1 で入れない理由: 審査員が URL で 30 秒で聴けることがデモ 25 点に直結し、残り日数で Swift/Kotlin を積むと核が薄くなる。台本の出口は増えても「原文のまま・時事なし」の検証は Worker 側で済んでいるので、器を替えても設計は変わらない。

## 3. 制約

- 期限 2026-11-08 20:00。1 人。公開リポ。初 commit を期間内に。
- musico-web / musico-react / virtual-dj-space / digline のコード・スキーマ・文言・UI を一切持ち込まない。README に「問題設定と学びだけを引き継いだ」と明記し、musico（2020）との違いを 3 点書く。
- 禁止領域（汎用 RAG、Streamlit、画像解析、教育チャットボット、メンタルヘルス、栄養、性格診断、医療、履歴書）に触れない。「癒し」は語っても「治療」「孤独の解消」は名乗らない。
- secret は環境変数（Cloudflare secrets）。リポに入れない。
- 「見つけた声」は短い引用（1 件 100 字程度まで）、投稿者名と元 URL を必ず付け、「この番組へのお便り」と別枠で表示し、削除依頼の口を置く。
- 未成年を想定した設計はしない（年齢確認はしないが、ラジオネーム以外の個人情報を集めない）。
- 最初のお便りは本物だけ。本人が 20〜30 通を書き、知人（伊豆部、甥、本職 DJ など）に数通ずつ協力を頼む（本人が依頼する。2026-11-03 決定）。知人のお便りを公開デモで使う了承は、依頼時に取る。
- Spotify 連携は開発モードのまま運用する（許可リストの本人と知人だけ）。審査員と一般の人は URL 貼り付けか「好きなもの 3 つ」で入る。README に明記する。

## 4. 決まっていること（本人の決定）

### 4.1 聴く体験
- 器は「流れ続けるラジオ」。アプリ（Web、スマホのブラウザ可）を開くと番組が流れ、画面に紹介中の作品の情報（ジャケット・表紙・ポスター、題名、作者）と、読まれているお便り（原文）が出る。
- 聴く場面は仕事中の BGM。聴くだけでよく、返事は義務でない。
- 聴き終えたあとの導線: 「もう一度体験する」（Spotify / YouTube / Amazon / Netflix 等へ送り出す）、「私も」、一言、「自分も一通置く」。
- 対象は音楽・本・映画の三つ。

### 4.2 お便り
- その場で出る一行（Instagram のストーリーに共有する感覚）。長文も内省も求めない。
- 置くときの材料: (a) **URL の貼り付け**（Spotify / Apple Music / YouTube / Amazon / 書店サイト / Netflix / Filmarks / Letterboxd などの作品ページの URL を貼ると作品が立ち上がり、一言を添えられる。本人決定。ブックマークレットで今見ているページから 1 タップで開ける）、(b) 自分の Spotify 履歴（最近聴いた・よく聴く・保存した曲。開発モードの許可リスト内）、(c) 番組で流れた作品、(d) 検索。
- DJ は履歴の作品について問いを 1〜2 個投げて引き出す（「2019 年によく聴いていたこの曲、何があった年？」）。答えなくてもよい。
- 一通に付くのは: 作品、本文（原文のまま）、ラジオネーム、土地（自由記述、粗くてよい）、年（任意）、言語。

### 4.3 DJ
- 声は各ユーザーが選ぶ。40 代の落ち着いた感じ。日本語から始め、次は英語。
- 曲とお便りの間に、自分の感想を少し言う。無口な DJ ではない。「次にこれをかける理由」も言う。
- 言ってはいけないこと: 時事。お便りの言い換え。出典の無い声。ラジオネームと土地と年以外の個人情報。「寂しい人のため」のような重い言葉。
- 「見つけた声」を読むときは、お便りと区別して「ネットで見つけた声です。〇〇さん、YouTube のコメントから」と出典を言う。

### 4.4 番組の組み方（三枠とダイヤル）
| 枠 | 中身 | 学習 |
|---|---|---|
| 近く | 本人の履歴とお便りから、誰かの理由が付いたもの | する（履歴と「私も」から） |
| 隣 | 本人の好きなものを好きな人が、他に好きなもの | する（声のつながりから） |
| 遠く | 世界のどこかの一通。本人との接点は問わない | **しない**。常に一枠ある |
- 「遠く」の強さはダイヤルで聴く側が動かす（セレンディピティの強さの調節）。パーソナライズは「近く」「隣」にだけ効く。

### 4.5 豊かになる紹介
- 作品はページになり、世界の一言が原文のまま溜まる。DJ の紹介はその溜まりから組む。一人目の声だけなら一行、十人目が来たら幅が出る。要約で潰さない。

### 4.6 リアクション
- 種類は「私も」と一言コメントの二つ。どちらもお便りの一種として扱い、DJ が声として読む。
- 本人のページでは、自分の置いたものに誰（ラジオネーム・土地）がどう反応したかが見える。合計数・ランキングは出さない。
- 反応が集まった作品は「反響の多かった一曲」として番組に再登場する（順位ではなく再登場）。

### 4.7 材料の三層
1. 本人の履歴と貼り付け（Spotify OAuth、作品 URL）
2. この番組へのお便り（世界の誰か）
3. 見つけた声（YouTube コメント。公式 API、名前と元リンク付き、別枠表示）

### 4.8 出口
- アプリの画面（ブラウザ標準の音声合成で DJ が話す。声は端末の声から選ぶ）
- クラウド TTS の口（デモ用。Google Cloud Text-to-Speech の Gemini-TTS。自然文のプロンプトで「40 代の落ち着いた深夜ラジオの DJ、ゆっくり、ささやくように」と指示できる。日本語 GA。本人了承 2026-11-03）
- MCP の口（remote MCP、Streamable HTTP）。Claude の custom connector、ChatGPT の Developer mode、Gemini の Connected Apps、Claude Code や個人のアシスタントから、同じ台本を取り出せる。他社アシスタントの中では「原文を変えない」保証ができないことを README に明記する。

### 4.9 技術スタック
- Cloudflare Workers + Hono（本人決定）。
- フロント: Hono JSX でサーバー描画、プレイヤーだけ hono/jsx/dom のクライアント部品。Vite + @cloudflare/vite-plugin。1 つの Worker（Claude の判断、notes/29。次点は Astro 7）。
- データ: Cloudflare D1。お便りは JSON で持ち出せる。
- Hono は安定版 4.13 系。HonoX は使わない（alpha）。
- 音声: ブラウザ標準の Web Speech API を既定にし、デモ回と各リスナーの最初の回だけ Gemini-TTS（Google Cloud Text-to-Speech、鍵は `GOOGLE_TTS_API_KEY`）。PWA（manifest + Media Session API）でスマホのロック画面から再生・一時停止・次へを操作できるようにする。ネイティブ化は v2（§2.1）。
- 名前: Dococa FM。ドメイン候補 `dococa.fm`（空き確認は DNS のみ。正式確認は本人）。

### 4.10 運用上の決め（Claude の判断。builder check Q6〜Q8 への回答）
- **本と映画の間の音**: DJ の声の下に権利フリー（CC0）の静かなベッド音を敷く。映画の予告編は自動再生せず、タップで。番組が終わったら次の回を自動で続け、再生中に次の回を先に作っておく（「流れ続ける」を満たす）。
- **費用**: 回はキャッシュし、1 人あたり 1 日の生成回数に上限を置く（既定 10 回）。クラウド TTS は本人のデモ回と、各リスナーの最初の 1 回だけに使い、以降はブラウザの音声合成に落とす。上限値は環境変数。
- **不適切投稿**: 公開前に Claude で判定（中傷・宣伝・個人情報・無関係）し、落ちたものは本人にだけ理由を返す。通報リンクを各お便りに置く。手動承認は入れない。
- **削る順（本人承認）**: 核（番組の生成と再生、お便り、URL 貼り付け、作品ページ、ダイヤル、検証 4 項目、Spotify、好きなもの 3 つ入力、見つけた声）は削らない → MCP の口とクラウド TTS → 翻訳 → eval の自動化（手動で 20 回分）。MCP で Claude に読ませるデモ場面は、間に合わなければ動画で見せる。

## 5. Claude の使い方（審査「Claude 活用」の中身）

- **台本係**: 作品・お便り・見つけた声・反応を入力に、DJ の発話（相槌、短い感想、次にかける理由、出典の読み上げ）を構造化出力で生成。お便り本文は入力をそのまま埋め込む。
- **問い係**: 履歴の作品について、一言を引き出す問いを 1〜2 個作る。
- **選曲係**: 「隣」と「遠く」の候補を、声の内容のつながり（同じ年、同じ土地、同じ気分、同じ言葉）から選ぶ。一致率を出さない。
- **翻訳係**: 他言語のお便りを日本語で読めるようにする。訳文はお便り作成時に 1 回だけ生成して保存し、DJ は保存済みの訳文を読む。画面には原文を併記する。検証は原文と保存済み訳文の両方に完全一致で行う（Claude の判断、Q5）。
- **検証（決定的コード、Claude に任せない）**: (1) 台本中のお便りが DB の原文と完全一致、(2) 見つけた声に URL と投稿者名がある、(3) 時事語（年号・今日・ニュース・流行語の辞書）を含まない、(4) ラジオネーム以外の個人情報を含まない。落ちた台本は出さず、作り直す。
- **道具の制限と hooks**（Claude の判断、builder check Q3 への回答）: Claude Agent SDK は Node のプロセスなので Worker 内では動かない。番組生成は Worker から Messages API を tool use で呼び、台本係に渡す道具を「お便りを ID で引く」「作品を ID で引く」の読み取りだけに絞る。書き込みや URL の生成は道具に無いので物理的にできない。Agent SDK と hooks は、ローカル（Node）で回す eval と見つけた声の収集バッチで使い、「AI がしないこと」の実演はそこで見せる。1 つの Worker の構成は崩さない。
- **eval**: 本人の履歴から作った 20 回分の番組で、検証 4 項目の通過率と「遠く」枠の出現率を測る。数字 1 つ: 「DJ の発話のうち、出典（お便り・見つけた声・作品データ）を持つ文の割合 100%、原文改変 0 件」。

## 6. デモ（審査「デモ」）

1. 本人の Spotify 履歴と、見つけた声から作った 3 分の回を流す（日本語、クラウド TTS）。画面に作品とお便りが流れる。
2. 審査員が好きなものを 3 つ入れる（または作品 URL を貼る）と、1 分で自分の回ができる。ダイヤルを「遠く」に回して違いを聴く。
3. ~~同じ回を Claude のアプリから MCP で取り出し、Claude の声で読ませる。~~（MCP は追記 L で撤去。代わりに、ホームの「いま届いているお便り」のカードを押すと、そのお便りからラジオが鳴り、「私も」と一言を返すところを見せる。2026-11-07）
4. 作品ページで、声が増えると紹介が変わるのを見せる（お便りを 1 通足して再生成）。

## 7. データの概略（詳細は builder）

- Item: 種別（music / book / film）、外部 ID（Spotify / iTunes / ISBN / TMDB 等）、題名、作者、年、画像 URL、プレビュー URL、送り出し URL
- Letter: item、本文（原文）、ラジオネーム、土地、年、言語、種別（letter / found / reply / watashimo）、出典 URL と投稿者名（found のみ）、作成者
- Listener: ラジオネーム、土地、声の選択、ダイヤル、言語
- History: listener、item、出所（spotify / url / manual）、日付
- Episode: listener、台本（構造化）、作品の並び、生成日時、検証結果
- 持ち出し: 自分のお便りと履歴を JSON で書き出せる

## 8. builder に任せること

- 画面の設計（personal-design skill のパレットとボイスを使う。個人プロジェクト）
- D1 のスキーマ詳細、ルーティング、i18n の辞書構造
- ~~クラウド TTS の提供元~~ → Gemini-TTS に決定（§4.8、§4.9。2026-11-03）
- 認証の方式（Spotify ログインと、リンクだけで聴けるゲスト。パスワードは持たない）
- MCP の認証（OAuth が間に合わなければ、設定画面で発行するトークンを Authorization ヘッダで）
- プレビューの取得元（iTunes Search API を既定、Spotify preview を補助、無ければ YouTube 埋め込み）
- 本と映画のメタデータの取得元（Open Library / Google Books、TMDB / OMDb）
- URL 貼り付けで対応するサイトの優先順位（Spotify / YouTube / Apple Music / Amazon / Filmarks / Letterboxd / 書店サイト。OGP の題名から作品検索へ落とす汎用経路を必ず持つ）とブックマークレット
- 見つけた声の収集量と品質の絞り方（YouTube Data API の quota 内）
- 一回の番組の長さ（既定 5〜7 作品、3〜5 分）
- 時事語の辞書の中身

## 追記 2026-11-03: デモ用ペルソナ

本人の決定（2026-11-03 夜）。デモの密度を出すため、AI が作った架空の多国籍ペルソナ（ダミーのリスナーアカウント）が、好きな作品に一言ずつお便りを書く。

- 日本語圏以外のペルソナは英語で原文を書いた体にする。番組では聴く側の言語（v1 は日本語）への訳を読み、画面には原文を併記する（§5 の翻訳係の形）。

## 追記 2026-11-05: Web の体験の組み替え（本人フィードバック。Phase 2 の正本）

本人の決定（2026-11-05、FigJam の F12）。§4.1〜§4.2 と §4.9 の一部を次のように読み替える。書き換えではなく、上書きする決定の一覧。

### A. 入口は「局」。スイッチを入れたら流れ続ける
- ホームはラジオの画面。スイッチをオンにすると、登録もログインも無しで、世界のどこかの誰かの好きなものを語る DJ の声が自動で連続再生される（最初は「遠く」の枠だけで組んだ回。回が終わる前に次の回を作っておく）。
- 画面は回単位ではなく局単位。ラジオらしい操作（再生 / 停止 / 音量）、いま流れている作品のカード（題名・作者・ジャケット、読まれているお便り、付いている反応と一言、出口リンク）、次に流れる作品の列。
- 聴いている途中で、流れている作品にその場で「私も」と一言が置ける（再生は止めない）。
- 「好きなもの 3 つ」（はじめの一歩）は入口ではなく、聴きながら自分の局を育てる導線に下げる。好きなものを登録すると「近く」「隣」の枠が効き始める。

### B. 誰が何をできるか（識別）
- 匿名（cookie のリスナー）: 聴く、私も、一言。
- サインイン済み: 加えて、好きなものの登録、Spotify などからの取り込み、自分の好きなものだけのラジオの公開、自分の好きなものに付いた反応・一言・共感した人の一覧（マイページ）。
- 識別は Google でサインイン（OIDC、`/auth/google` → `/auth/google/callback`）。Cloudflare Access は使わない（消費者向けでなく、人数課金のため）。サインインすると、そのときの cookie のリスナーに Google の subject を紐づける（別端末でサインインしたら同じリスナーに戻る）。匿名のまま置いた私も・一言は、その端末のリスナーのまま。
- 一言（コメント）は匿名でも置ける（§4.6 のまま）。本人の 3 の「コメントには識別が要る」は、マイページで自分の一言を辿れることを指すと解し、置く行為自体は匿名可とする。

### C. 自分の好きなものだけのラジオ（公開局）
- サインイン済みのリスナーは、自分の好きなもの（登録した作品）だけで組んだ局を公開 URL で持てる（例 `/stations/<slug>`）。誰でも開けて、スイッチを入れると、その人の好きなものと、それに世界から付いたお便りで番組が流れる。
- 公開するかはそのリスナーが設定で選ぶ（既定は非公開）。

### D. 取り込みの並び
- Spotify の取り込みから「好きなもの」を登録しやすいよう、よく聴く曲（短期・中期・長期の順位）と最近聴いた曲の順で並べて見せる。再生回数そのものは Spotify API が出さないので使わない。「数で人を測らない」は番組と DJ の規則であり、本人が自分の履歴を並べ替える UI には適用しない。

### E. 見た目と文言
- 全体にラジオ感を押し出した UX ライティング（「お便り」「局」「ダイヤル」「DJ」）。
- レイアウトはスマホ対応のモダン、テイストはレトロフューチャー / シティ・ポップ。番組のコントロールはレトロなラジオの意匠（ダイヤル・針・トグル）。
- キービジュアル: 机に座ってレトロなラジオを聴く人と、そのラジオに世界中の誰かの好きなものがつながっているイメージ。

### F. 言語設定（本人追加 2026-11-05）

### H. 本人追加 2026-11-05（夜）: 音声の事前生成、合間のトーク、声、土地の選択式

- **BGM**: トークとは別音源（いまの `bed.mp3` のループ）で、枠ごとに替えられる。

- **土地は選択式**: 自由記述をやめ、国（ISO 3166-1）と、国によっては都道府県／州（日本の 47 都道府県、アメリカの州）の 2 段の選択にする。保存は `place_country` と `place_region`、表示と DJ の読みは「島根」「Portugal」のように粗い粒度のまま。既存の自由記述は表示用に残し、新規の入力だけ選択式にする。 お便りに付く土地のラベル（`letters.place`）は言語設定に関わらず日本語で保存する（DJ が日本語で読むため。英語設定のリスナーの画面にも「島根」と出る。英語表示は Phase 3 で、コードから引き直す）。

### I. 本人指摘 2026-11-05（夜）: DJ は「かけない」。紹介して、お便りを読む
- この局では曲や映像は流れない。流れ続けるのは「誰かの好きなものについての語り」だけ。したがって「次は〇〇です、どうぞ」「次にかける理由」のような再生を前提にした言い回しは使わない。
- 単位の流れ: 作品の紹介 → 「〇〇さん（土地）からのお便りです」 → お便り本文（原文どおり）→ DJ の短い感想。つなぎは「続いては、〇〇さんから、『作品』へのお便り」のように、次に来るのがお便りであることを言う。「どうぞ」は言わない。
- 検証に禁止語を足す: かけます／かけましょう／流します／お聴きください／聴いてください／観てください／お楽しみください など、再生や視聴を促す語。作品を聴きたい人には画面の「この作品を聴く・観る」の出口を使ってもらう。
- 台本の枠は「作品の紹介とお便りへの手渡し」「感想と次のお便りへのつなぎ」の 2 つ。
- 画面の「このあと流れるもの」は「このあとのお便り」（作品名と送り主）。
- 声は男性 Charon で確定（本人試聴 2026-11-05、候補 P）: シックでダンディ、終始落ち着いた穏やかな話し方で音量控えめ、テンポは滑らかに前へ進み抑揚は豊か、固有名詞と作品名で少し声を立てる。英語は同じ方向の指示（候補 Q）。指示文は `src/worker/tts/style.ts`。
- 英語の発話（DJ も英語）は Phase 3 の事前生成で「単位ごとに日本語と英語を作る」形で入れる。それまで英語設定は英語 UI + 日本語 DJ。

### J. 本人追加 2026-11-05（夜）: 聴いた履歴（サインイン済み）
- サインイン済みのリスナーは、マイページで「聴いたお便り」を見られる: 自分の回（検証済み）で読まれたお便りを新しい順に（作品名、送り主のラジオネームと土地、聴いた日）。集計の数字は出さない。

### K. Phase 3 の構造（追記 H・I・J を実装に落とす。2026-11-06）
- **単位（unit）**: 「お便り × 作品」ごとに DJ の語りを 1 回だけ作る。単位は `intro`（作品の紹介。送り主の名前は言わない）と `after`（短い感想。次のお便りの中身には触れない）の 2 行。手渡し「〇〇さん（土地）からのお便りです」は定型（`script.letterFrom` / `script.foundVoice`）で、模型が書かない。単位は作ったときに検証（既存の `verifyEpisode` を 1 枠で回す）し、通らなければ `verified = 0` で保存して語りを使わない（定型だけで読む）。言語ごとに 1 行（`units (letter_id, lang)`）。
- **番組（episode）**: 選曲（`selectProgram`）はそのまま。台本は枠ごとに模型を呼ばず、単位を並べる。無い単位はその場で作る（お便り投稿時と 15 分ごとの定期処理が先に作っておくので、通常は無い）。枠の並びは「つなぎ（定型）→ intro → 手渡し（定型）→ お便り本文（原文どおり）→ after → 反応（定型）」。同じ作品に 2 通目以降は「同じ作品に、もう一通」のつなぎと手渡しだけで、intro は 1 通目のもの。番組の検証は従来どおり全体に掛ける。
- **つなぎの定型（bridge）**: 冒頭、枠の種類（近く・隣・遠く）、同じ作品のもう一通、終わり、の定型文を i18n に持つ（`bridge.*`）。`fixed` 行として置き、`FIXED_TEMPLATES` に加える。差し込み語を含むつなぎは作らない（手渡しの定型がその役）。時を示す語（今夜など）は入れない。
- **音声**: 行の音声は「言語 × 声 × 本文の SHA-256」を鍵に R2 に置く（`tts/v2/<lang>/<voice>/<hash>.mp3`）。同じお便りは誰の番組でも同じ音声を使い、定型のつなぎと手渡しは一度作れば全員に使える。クラウドの声は鍵（`GOOGLE_TTS_SA_JSON`）があれば全員の全番組に付ける（「最初の 1 回だけ」をやめる）。歯止めは「1 日に合成する行数」（`CLOUD_TTS_GLOBAL_DAILY_LIMIT`、既定 3000、日本時間、`tts_audio` を数える）。超えたら `/tts` は 503 を返し、プレイヤーはブラウザの声に切り替える。
- **事前生成**: お便りが保存されたら（`POST /letters`、MCP `post_letter`、`/admin/letters`、`/admin/found`）`waitUntil` で単位と音声を作る。Cron（15 分ごと）が、単位の無いお便りと音声の揃っていない単位を 1 回 20 件まで埋める。`POST /admin/prepare` で同じ処理を手で回せる（デモデータの投入後に使う）。反応（私も・一言）は定型文だけなので単位を持たない。
- **聴いた記録**: プレイヤーがお便りの行を読み始めたときに `POST /listens`（番組 id、お便り id、枠の添字）を送る。`listens` は（リスナー、お便り）で 1 行、最新の日時に更新。マイページの「聴いたお便り」はこの表から出す（生成済みの番組から導くのをやめる）。
- **土地**: お便りに `place_country` / `place_region` を持たせ（送ったときのリスナーの値を写す）、画面の表示は言語に合わせてコードから引く。DJ の日本語の読みは `place` のまま。
- **英語の DJ**: 単位を言語ごとに作る（`lang = en` は英語の指示文で intro / after を書き、お便りは `body_en`（無ければ原文）を読む）。番組は聴く人の言語で組み、`episodes.lang` に持つ。音声は `en-US` と `DJ_STYLE_PROMPT_EN`。検証は英語用の語彙（時事・数え上げ・再生の誘い）を別に持つ。
- **お便りの無い作品**: 番組に入れない（本人決定 2026-11-06）。Phase 1 の予備プール（`FALLBACK_SQL`）と公開局の例外を外す。他人のお便りがまだ無い新規リスナーは、近く・隣の席が遠くで埋まる。
- **順番**: 上の順（お便りの無い作品 → 音声の鍵 → つなぎ → 単位 → 事前生成 → 聴いた記録 → 土地 → 英語）。締切（2026-11-08 20:00 JST）に掛かったら、後ろから落とす。

### L. Phase 4（本人フィードバック 2026-11-06、Phase 3 のデプロイ後。本人決定を実装に落とす）
- **お住まい**: 画面の「土地」を「お住まい」に（英語 "Where you live"）。DJ の手渡しはラジオの定番に揃え、「{お住まい}にお住まいの、{名前}さんからのお便りです。」（英語 "A letter from {name}, who lives in {place}."）。反応の定型も同じ言い方で送り主を言う。画面の送り主表記「〇〇さん（東京）」は変えない。文言を変えた定型行の音声は作り直しになる（短い行だけ）。
- **ダイヤルはラジオ面のノブ**: 設定のスライダーをやめ、ラジオ面にノブを置く。値（0〜1）はブラウザの `localStorage`（`dfm.dial`）に持ち、次の枠を頼むときに送る。サインイン済みなら `listeners.dial` にも写し、別の端末の初期値にする。
- **枠ごとの番組（リアルタイムのセレンディピティ）**: 回を 6 枠まとめて作るのをやめ、1 回 = 1 枠にする。プレイヤーは今の枠が終わる前に次の 1 枠を「今のダイヤル値」で頼む（先読みは 1 つ。ダイヤルが動いたら先読みを捨てて取り直す）。冒頭のつなぎ（`bridge.open`）は、この聴取の最初の枠（クライアントが `first` を送ったとき）だけ。終わりのつなぎ（`bridge.close`）は使わない（止めると静かに止まる）。回の保存・再開・`/listens`・「もう一度聴く」の仕組みは 1 枠の回でもそのまま。1 日の上限（`EPISODE_DAILY_LIMIT` / `EPISODE_GLOBAL_DAILY_LIMIT`）は枠の数として数え直し、既定は 6 倍。
- **遠さ（embedding）**: 作品ごとに「題名・作者・年・種類」（作品は説明文を持たない。実装時の確定 2026-11-06）の埋め込みを Workers AI（`@cf/baai/bge-m3`、多言語）で 1 本作り、`items.vec` に持つ（作品ができたときに作り、無いものは Cron と `/admin/prepare` が埋める）。聴く人の嗜好は「好きなもの」の埋め込みの平均。好きなものが無ければ「聴いたお便り」（`listens`）の作品から、それも無ければ嗜好なし。お便り候補の遠さは、嗜好との cosine 距離の候補内での順位（0〜1）。ダイヤル d のとき、遠さが d±0.2 の候補から無作為に選ぶ（無ければ幅を広げる）。最近聴いた作品（`listens`）とこの聴取で流した作品は避ける。嗜好なしなら無作為（世界のラジオと同じ）。近く・隣・遠くの枠の名はつなぎの選択にだけ残す（遠さ < 1/3 近く、< 2/3 隣、それ以上遠く）。公開局と世界のラジオの選び方は変えない。距離の数値は選ぶためだけに使い、画面にも DJ にも出さない。
- **MCP を外す**: `/mcp` のルート、設定の表示、README・SECURITY.md・DESIGN.md の記述を消す（コードは git に残す。`listeners.mcp_token` の列は残して使わない）。
- **ホームは「いま届いているお便り」**: 「最近の作品」を、最新の公開のお便り（お便りと見つけた声。一言は除く）6 通のカードに。作品のサムネイル（`items.image_url`、無ければ無地）とお便りの本文（画面上は 120 字で切って「…」。原文は作品ページで全文）を主役に、作品名・ラジオネーム・お住まいは小さく。押すとその作品のお便りから自分のラジオが始まる（最初の枠にそのお便り）。
- **お便りを送るページ**: パネルと余白を DESIGN.md のトークンで組み直す。作品の指定は「URL を貼る」と「好きなものから選ぶ」（取り込んだ Spotify と手で足したもの。題名で絞り込み）の 2 本。サインイン済みなら題名で探せる（iTunes（Spotify の検索は client secret が要るため、鍵の要らない iTunes で代える。実装時の確定 2026-11-06）・TMDB・YouTube・Google Books を `GET /put?q=` で横断。匿名には「サインインすると探せます」。レート制限の対象）。「Spotify をつなぐ」は設定へ移す。ブックマークレットは、ブラウザのブックマークバーへドラッグするボタンと 3 行の説明。
- **マイページ**: パネルで組み直す。好きなものはサムネイル付きのカード、聴いたお便り・届いた反応・公開ラジオは既存の内容のまま見た目を整える。サインアウトはヘッダだけ。
